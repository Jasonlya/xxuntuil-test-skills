# 可测性四问与自动化分级

阶段三用这份文件。前半是四问（判「能不能测」），后半是 A/B/C（判「值不值得自动化」）。

两件事顺序不能颠倒：**先证明能测，再讨论自动化。** 一个观测点都写不出的规则，讨论 A 还是 B 没有意义。

---

# 一、可测性四问

对第 6 段每条 `REQ-*` 逐条问。四问的答案写进第 9 段，一条规则一行，四项都要填。

## OBS｜观测点：结果在哪看

这是四问里最重要的一问。**写不出观测点的规则，在当前架构下就是不可验证的规则**——不是「暂时没想好」，而是「系统没有暴露任何可以判断真假的信号」。

合格写法要具体到**位置 + 字段 + 期望值**：

| 不合格 | 合格 |
|---|---|
| 看订单状态对不对 | `GET /orders/{id}` 的 `status` = `PAID`；同时 `order_payment` 表新增一条 `state=SUCCESS` |
| 检查有没有发消息 | 消息队列 topic `order.created` 消费到 1 条，payload 中 `orderId` 与订单一致 |
| 看页面提示正确 | 接口返回 `code=40021`，前端 toast 文案取 `i18n.err.40021` |
| 看数据统计对不对 | 报表接口 `total` = 该 user 在窗口期内 `status=PAID` 的订单金额之和，可用 SQL 独立复算 |

**观测点的优先级**（越靠前越可信）：

1. 接口响应字段
2. 数据库最终状态
3. 消息 / 事件是否投递及内容
4. 日志与埋点
5. UI 元素与文案

UI 排在最后，因为它最不稳定、最容易被样式改动打破，且无法区分「数据错」和「展示错」。

**写不出观测点时**，在第 9 段判 `OBS-缺失`，并在第 11 段记一条未决项：要么补观测手段（加日志 / 加接口 / 加埋点），要么裁定本版不验证。**不允许写「通过人工观察确认」。**

## CTRL｜可控性：前置状态怎么造

回答三件事：**能不能造、怎么造、造一次多久。**

| 维度 | 要写的内容 |
|---|---|
| 造法 | 调接口 / 直接写库 / 走后台管理页 / 用挡板返回固定值 / 只能等真实数据出现 |
| 耗时 | 秒级 / 分钟级 / 小时级 / 天级（跨天任务） |
| 副作用 | 造完要不要清理、清理是否影响其它数据 |

「造一次要等 3 天」和「造一次 3 秒」在自动化分级上是两个世界，必须写清。

**高危信号**：只能靠「生产数据回流」或「等某个运营真的操作一次」才能构造的前置——这类基本直接落 C。

## ENV｜环境依赖：跑起来需要什么

- 依赖哪些外部服务（支付、短信、推送、三方风控）
- 这些服务在测试环境是**真实、沙箱、还是挡板**
- 是否需要特殊数据（脏数据、超大数据量、特定账号）
- 环境是否独占（跑的时候别人能不能用）

**关键判断**：依赖服务在 CI 里可用性如何？如果某个依赖在 CI 经常超时，那这条规则最多只能到 B。

## TIME｜时序可控性

- 是否依赖等待（异步回调、轮询、延迟队列）
- 是否有定时任务，频率多少，能不能手动触发
- 是否有超时窗口、重试次数、退避策略
- 是否跨天 / 跨时区

**「等 30 秒看看」不是时序可控**，那是不稳定的固定 sleep。可接受的做法是：能手动触发定时任务、能调小超时参数、或能通过注入时间源控制。

# 二、自动化分级 A / B / C

## 判定顺序（不要跳步）

```
① 结果能不能机判？        不能 → C
② 能机判，且满足全部常驻条件？ 是 → A
③ 能机判，但有一项不满足 → B
```

很多人从 A 开始判，结果把不稳定的用例全塞进 A，三个月后整条流水线红得没人看。**先判「能否机判」，再判「能否常驻」。**

## A｜可进常驻 CI 回归

六个条件**全部**满足才是 A：

| 条件 | 判据 |
|---|---|
| 结果可机判 | 有确定的断言，不需要人看图、看文案、凭经验判断 |
| 数据自洽 | 用例自建前置、跑完自清，不依赖公共环境的残留数据 |
| 无人工介入 | 无验证码、无人工审核、无需实人操作 |
| 时长可控 | 单条 < 2 分钟，或可并行拆分 |
| 环境稳定 | 依赖服务在 CI 中可用，无频繁超时 |
| 非时序脆弱 | 无固定 sleep、无强竞态、无跨天依赖 |

**成本参考**：编写 0.5–2 人时 / 条，维护约 0.1 人时 / 月。

## B｜可自动化，但不进常驻回归

结果可机判，但有一项不满足：

- 前置数据重（需要预置大量数据或专属账号）
- 需要专属环境或挡板配置
- 单条执行 > 2 分钟
- 依赖服务在 CI 不稳定

**触发方式**：夜间定时跑 / 发版前手动跑 / 改动相关模块时跑。

**成本参考**：编写 2–8 人时 / 条，另加环境与数据维护成本。

## C｜只能手工或探索

满足任一条即 C：

- 结果需要人判断（视觉效果、文案语气、交互手感、「业务上是否合理」）
- 前置无法稳定构造（需要真实用户数据、生产流量、线下资源）
- 一次性场景（数据迁移、限时活动、临时开关）
- 依赖不可自动化的第三方（短信到达、真实支付、人脸核身）

**成本参考**：0 编写成本，每次执行 0.5–2 人时。

## 常见误判

| 误判 | 为什么错 | 正确判法 |
|---|---|---|
| 「接口能调通，就是 A」 | 只测了成功态，失败态与数据一致性都没覆盖 | 看断言是否覆盖第 6 段的规则本身，不是覆盖「接口通」 |
| 「有脚本能跑，就是 A」 | 脚本里有 `sleep(30)` 等异步，实际经常假绿 | 有时序依赖 → 最多 B |
| 「手工点一遍很快，就是 C」 | 能机判的场景手工做是浪费 | 先看能否机判，能机判就不该是 C |
| 「这次先手工，下次再自动化」 | 没有记录原因的「下次」等于永远不做 | 判 C 必须写明不能自动化的具体障碍 |
| 全部都判 A | 不稳定的用例污染常驻回归，最终整条流水线被忽略 | 严格按六条件逐项核 |

## 判 C 必须写清障碍

这是本 skill 唯一强制要求「写原因」的分级。格式：

```
AUTO-07｜REQ-05 退款到账通知｜C｜障碍：依赖真实支付渠道回调，测试环境无沙箱，
仅能生产小额实付验证；每次 1 人时｜复核条件：接入支付沙箱后重评为 B
```

「复核条件」这一栏很重要——它把「以后再说」变成一个**可触发的条件**，而不是一句空话。
