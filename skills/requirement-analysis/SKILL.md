# 需求分析（requirement-analysis）

把「一份需求」变成「一份离开文档后仍能被独立验证的模型」。

## 为什么需要它

需求分析的常见产出是「测试点清单」。但清单解决不了落地的问题：**结果在哪看、状态怎么造、依赖哪些环境、能不能进 CI**。这四个问题没有答案，用例写得再全也进不了回归，只能停在文档里。

三个具体的坑，本 skill 就是为它们设计的：

1. **误读一条规则的代价远大于漏一个测试点。** 漏点会在评审时被发现；误读会被放大成几十条用例和几天人时，而且要等到联调才暴露。所以每条结论必须能指回来源，指不到的一律降级为未决项。
2. **口头需求在三个月后无法追溯。** 「当时某某说这样就行」——没有记录，就无法判断实现是否符合预期。所以口头来源必须同时挂一条未决项，等书面确认。
3. **「快、稳定、支持多端」这类词不可测。** 没有数值的非功能约束，到执行阶段一定会有人临时编一个阈值。所以在分析阶段就把无数值的项判为未决项，而不是留给下游猜。

## 落盘产物

| 文件 | 内容 | 维护方 |
|---|---|---|
| `{项目}/需求模型.md` | 十二段模型，**唯一人工维护源**，未决项与裁决都写在这一个文件里 | 人 |
| 闸门输出 | 每次跑 `req_lint.py` 的 stdout，可直接贴进评审记录 | 脚本 |

单文件是刻意的：模型、未决项、裁决混在一个文件里，文件本身就是状态，不需要额外的进度表。

模型的结构不由散文约定，而由 `assets/req-model.schema.json` 定义——十二段的顺序、每段由哪些块组成、每个表格必须有哪些列、每列承担什么语义，全在那里。`req_lint.py` 读它做校验，不自己写死一套。详见下文「输出契约」。

## When to Use

- 拿到 PRD / 需求单 / 技术设计，要先把「这个需求到底要做什么」定下来再进入测试
- 多来源并存（需求文档 + 接口定义 + 代码 + 缺陷单），需要交叉核对、暴露矛盾
- 需要判断这个需求**值不值得自动化、能自动化到什么程度**
- 需求评审前，要一份能拿着逐条问的清单

## When NOT to Use

- 写测试用例 → 不在本 skill。本 skill 只输出「系统是什么」，不输出「怎么测」
- 定测试深度 / 测哪些类型 → 不在本 skill
- 已确认缺陷的根因分析 → 不在本 skill
- 完全无文档且系统陌生 → 先探索，有了系统理解再回来建模

**本 skill 完全自包含**：不读、不引用其它 skill 的任何文件，单独安装即可完成全部工作。

## 五条铁律

1. **来源不可省。** 每条规则、字段、状态、接口都要能指到章节 / 接口路径 / 代码行。指得到的用 `[SRC-*]` 标注；只能指到人的，标 `[SRC-VERBAL]` 并**同时挂一条未决项**。口头需求不是需求，是待确认事项。
2. **空要写明，不能留白。** 某段确实没有内容，写「已核对，无此类要素」+ 依据。留白无法区分「没有」和「没查」——这是模型失效最常见的原因。
3. **不硬猜，也不无限期挂着。** 模糊项进第 11 段，必须写清「向谁确认」。不许自己编一个合理值填进正文，也不许只写「待确认」三个字。
4. **只描述「是什么」，不描述「怎么测」。** 唯一例外是第 9、10 段：可测性与自动化成本属于事实判断，不属于测试设计。
5. **数值优先于形容词。** 「响应快」不能进模型，「P95 < 300ms」才能。无数值的非功能约束一律判未决项。

## 来源分级与冲突裁决

| 标记 | 来源 | 可信度 | 附加要求 |
|---|---|---|---|
| `SRC-API` | 接口定义文件（OpenAPI / proto / Postman） | 最高 | — |
| `SRC-CODE` | 代码实现（`文件:行`） | 静态事实最高 | 需记分支与 commit |
| `SRC-DOC` | 技术设计 / 库表设计 | 高 | — |
| `SRC-REQ` | PRD / 需求单 | 高 | — |
| `SRC-TICKET` | 缺陷单 / 工单 | 中 | 标注是否已修复 |
| `SRC-VERBAL` | 口头 / 群聊 / 会议口述 | 低 | **必须同时挂未决项** |

**冲突裁决分两类，不可混为一谈：**

- **「实际是什么」**——静态事实冲突时以 `SRC-API` / `SRC-CODE` 为准（代码是运行时的真实行为）。
- **「应该是什么」**——以需求方裁决为准。**代码与需求不一致不是「以高优先级覆盖」，而是一条待确认的缺陷线索**，记入第 7 段（异常）或第 11 段（未决项），绝不能在模型里悄悄抹平。

> 这条区别很关键：如果一律「以代码为准」，实现里的 bug 会被写进需求模型，然后一路下游都被当作预期行为。

## 十二段模型

详细模板见 `assets/req-model-template.md`，**结构与列名的权威定义是 `assets/req-model.schema.json`**，闸门读 schema，不读模板。

| # | 段名 | 必须回答 | 闸门检查 |
|---|---|---|---|
| 1 | 目标与非目标 | 一句话目标 + 可量化成功标准 + **明确不做什么** | 非目标 ≥ 1 条 |
| 2 | 角色与权限 | 角色 × 能做 / 不能做 / 可见范围 | 每条带来源 |
| 3 | 状态与迁移 | 状态清单 + 合法迁移 + **非法迁移** | 每个状态 ≥ 1 条非法迁移 |
| 4 | 数据契约 | 字段 × 类型 / 必填 / 边界 / 来源 / 校验时机 | `FLD-*` 编号 + 来源 |
| 5 | 接口与依赖 | 接口 × 成功态 / **失败态** / 超时 / 重试 / 幂等 | `API-*` 编号 + 失败态非空 |
| 6 | 业务规则 | 规则正文（可被独立判定真假的陈述） | `REQ-*` 编号 + 来源 |
| 7 | 异常与降级 | 异常场景 → 系统行为 → 用户可见结果 | `EX-*` 编号 + 来源 |
| 8 | 非功能约束 | 指标 + **数值** + 测量方法 | `NFR-*` + 数值（禁形容词） |
| 9 | 可测性评估 ★ | 观测点 / 可控性 / 环境 / 时序 | `TST-*` + 观测点非空 |
| 10 | 自动化分级 ★ | A / B / C + 理由 + 成本 | 值 ∈ {A,B,C} + 理由 |
| 11 | 未决项 | 问题 + **向谁确认** + 影响 + 裁决 | `OQ-*` + 责任人 |
| 12 | 验证边界与移交 | 本期验什么 / **不验什么及理由** | 非空 |

★ 标记的两段是本 skill 与「泛需求建模」的分界：普通建模到「理解需求」就停了，这里必须再回答**能不能测、值不值得自动化**。

**编号规则**：`REQ-01` 业务规则、`ST-01` 状态、`FLD-01` 字段、`API-01` 接口、`EX-01` 异常、`NFR-01` 非功能、`TST-01` 可测性项、`AUTO-01` 自动化项、`OQ-01` 未决项。编号全局唯一、不复用；删除的编号留空不回收，否则下游引用会指错。

## 输出契约

模型不只是给人读的。它要能被下游直接消费——按 `REQ-*` 生成用例、按 `TST-*` 挑可自动化项、按 `AUTO-*` 排优先级。靠正则去刮一份散文式 Markdown 是不可靠的，所以结构必须先定下来。

契约在 `assets/req-model.schema.json`：12 段、13 张表、6 个小节、1 个代码块、69 个列定义。每列声明一个 **role**，闸门按 role 校验，而不是按段写死规则：

| role | 校验什么 | 拦住的问题 |
|---|---|---|
| `id` | `<前缀>-<两位以上序号>`，全局唯一 | 编号写 `REQ-3`、前缀张冠李戴、重复占号 |
| `source` | 必须含 `[SRC-*]`；含 `SRC-VERBAL` 的还要同行引用 `OQ-*` | 结论没有出处；口头需求被当成结论 |
| `ref` | 值必须是文档里真实存在的编号，且前缀在允许范围内 | `TST-01` 挂到不存在的 `REQ-99` |
| `enum` | 值 ∈ 声明集合（如 `是/否/条件`、`A/B/C`） | 分级写成 `P0`、终态写成「可能」 |
| `number` | 必须含数字 | 非功能指标写成「很快」 |
| `person` | 非空且不是「待确认 / TBD / ?」 | 未决项挂着但没人负责 |
| `text` | 非空、非破折号占位、满足 `min_len` | 必填格写 `—`；规则只写八个字 |
| `any` | 只查非空（若必需） | — |

有三件事散文写不出、只有 schema 能表达，也因此只有 schema 能机判：

1. **列的必备性**。第 5 段少了「失败态」这一列，和每行失败态都空着，是两种不同的错。前者是结构违约（E012），后者是内容缺失（E005）。
2. **跨表约束**。每个 `ST-*` 都要有对应的非法迁移（E004）；每条可测项都要有分级（W005）。这些都没法落在单张表里。
3. **移交索引与实际条目的一致性**。第 12 段那行 `A4/B2/C1` 是人手写的，模型改了分级它不会自动变。schema 声明了这行代码块的格式，闸门就去数实际条数（E014）——否则下游读到的是一份假数据。

改结构只改 schema，脚本不动；把 schema 改坏（段号断了、role 拼错、约束引用不存在的名字），脚本会以退出码 2 拒绝运行，不会带着坏结构继续判。

```bash
python3 scripts/req_lint.py --describe   # 按 schema 打印完整字段契约
```

## 工作流

### 阶段〇｜收料与可信度分级

**先要这些东西，缺的先记下、不等：**

- 需求侧：PRD / 需求单 / 原型 / 验收标准
- 技术侧：技术设计、库表设计、接口定义（OpenAPI / proto）、时序图
- 实现侧：代码仓库（**必须记分支名 + commit hash 或拉取时间**）
- 历史侧：相似需求的旧模型、缺陷单、线上问题记录

**基线是硬要求。** 没有 commit 的模型三个月后无法判断是否还成立，也无法划清「改动前 / 改动后」的边界。基线记在模型文件头部。

材料缺哪块，就在第 11 段记一条「缺 X，影响第 N 段，向 A 索取」，然后继续建模——不要因为缺材料停工，也不要因为缺材料就跳过那一段。

### 阶段一｜建模（十二段）

按模板逐段填。两个纪律：

- **先填指得到来源的，指不到的不要编。** 编出来的内容比空着危险，因为它看起来是结论。
- **每段填完自检一次**：这里的空，是「没有」还是「没查」？「没有」写结论，「没查」进未决项。

### 阶段二｜冲突与歧义扫描

加载 `references/ambiguity-patterns.md`，按八类模式**逐类过筛**材料（不是想起来才查）。

三类冲突分别处理：

| 冲突类型 | 例子 | 落到哪 |
|---|---|---|
| 文档内自相矛盾 | PRD 第 3 章说必填、第 7 章说选填 | 第 11 段 |
| 跨文档冲突 | PRD 与接口文档字段类型不一致 | 第 11 段 |
| 文档 vs 实现 | 代码允许的状态迁移，需求文档未提 | 第 3 段补录 + 第 11 段确认「是否预期」 |

扫描的目标不是把矛盾消灭，而是**把矛盾变成一条能被回答的问题**。

### 阶段三｜可测性与自动化判定 ★

加载 `references/testability-grading.md`。

对第 6 段每条 `REQ-*` 做四问，结果写进第 9 段：

- **OBS 观测点**：结果在哪看？接口响应 / DB 字段 / 日志 / 埋点 / 下游回调 / UI 元素。写不出观测点的规则，是当前架构下不可验证的规则。
- **CTRL 可控性**：前置状态能不能造出来、怎么造、造一次多久。
- **ENV 环境依赖**：需要哪些服务、要不要挡板 / 打桩、要不要脏数据。
- **TIME 时序**：是否依赖等待、轮询、定时任务、跨天；有无超时与重试窗口。

再对每个可测项判 A / B / C，写进第 10 段。**判 C 的必须写明「为什么不能自动化」**——否则半年后一定有人重新评估一遍，重复同样的结论。

### 阶段四｜澄清（⏸ 检查点，不代答）

- 一次问完，按影响面排序（影响规则数量多的先问）
- 每条问题给出「我的假设 + 若成立的影响 + 若不成立的影响」，让对方容易回答
- 拿到裁决写回第 11 段的「裁决」列，并注明裁决人与日期
- **无人在场（headless / CI）时**：全部保留为未裁决，取保守分支继续，并在第 12 段标注「基于假设 X，待确认」。不许伪造裁决

### 阶段五｜闸门与移交

```bash
python3 scripts/req_lint.py {项目}/需求模型.md
```

退出码 **1** 即不可交付，按报错逐条修，不要绕过。退出码 **2** 说明输入或 schema 本身有问题（文件读不到、schema 写坏），不是模型的问题。

想先看清结构要求再动笔：`python3 scripts/req_lint.py --describe`。想确认闸门本身没坏：`python3 scripts/selftest_req.py`。

移交时给一句话索引，方便下游直接判断要不要读全文：

```
需求模型.md · 18 条规则 · 3 个未决 · 自动化 A7/B5/C2 · 基线 main@a1b2c3d
```

这行由闸门对账（E014）：写的数字与实际条目不符会直接报错。

## Common Mistakes

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 把「待确认」写进正文当结论 | 下游基于假设写用例，全量返工 | 正文只写有来源的；模糊项进第 11 段 |
| 只写「待确认」，不写向谁确认 | 问题永远没人答 | 每条未决项必须有人和影响面 |
| 接口只写成功态 | 错误码、重试、幂等全漏，联调期暴雷 | 每个 `API-*` 至少一条失败态 |
| 非功能写「响应快、支持高并发」 | 不可测，执行期临时编阈值 | 带数值与测量方法，或判未决项 |
| 可测性只写「可测」 | 等于没说 | 四问逐项写，观测点必须具体到哪看 |
| 判 C 不写原因 | 半年后有人重新评估一遍 | 写明不能自动化的具体障碍 |
| 有代码就「以代码为准」 | 实现里的 bug 变成「预期行为」 | 静态事实以代码为准；应然以需求方裁决为准 |
| 空段落留白 | 无法区分「没有」和「没查」 | 写「已核对，无此类要素」+ 依据 |
| 编号删除后回收复用 | 下游引用指错条目 | 编号留空不回收 |
| 随手改表头列名或插一列 | 闸门按 schema 定位列，改名即判缺列；下游解析同断裂 | 改结构先改 schema，再同步模板 |
| 改了分级但没改移交索引 | 下游只读那一行，读到的是假数据 | 闸门 E014 会对账，改完分级重跑一次 |
| 必填格写「—」当没内容 | 看起来是填了，实际什么都没说 | 空就是空，没有就写依据并进未决项 |

## 与其它 skill 的关系

本 skill 只做一件事：把需求变成模型。写用例、定策略、根因分析都不在这里。

模型是纯 Markdown、纯文本表格，不依赖任何脚本或配置文件即可阅读。若宿主里同时装了本合集其它 skill，模型可直接作为它们的输入；但**本 skill 不引用它们的任何文件**，单独安装同样完整可用。
