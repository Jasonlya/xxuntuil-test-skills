# 需求分析（requirement-analysis）

把「一份需求」变成「一张能直接排测试的清单，每一行都带着出处」。

## 为什么需要它

需求分析的常见产出是测试点清单。清单的问题不是不够多，而是**没法验证**：写完没人能判断是否完整，也没人知道某一条是从哪来的，于是评审变成互相念稿。

三个具体的坑，本 skill 就是为它们设计的：

1. **误读一条规则的代价远大于漏一个测试点。** 漏点会被评审发现；误读会被放大成几十条用例和几天人时，而且要等联调才暴露。所以每条结论必须能指回原句，指不到的一律降级为待澄清。
2. **口头需求三个月后无法追溯。** 「当时某某说这样就行」——没有记录就无法判断实现是否符合预期。口头来源只能是弱证据，且必须同时挂一条待澄清。
3. **「快、稳定、支持多端」是不可测的。** 没有数值的约束，到执行阶段一定有人临时编一个阈值。分析阶段就要把它变成待澄清，而不是留给下游猜。

## 落盘产物

| 文件 | 内容 | 维护方 |
|---|---|---|
| `{项目}/需求测试分析.md` | 四块产物 + 移交索引，**唯一人工维护源** | 人 |
| 闸门输出 | 每次跑 `req_lint.py` 的 stdout，可直接贴进评审记录 | 脚本 |

单文件是刻意的：产物、证据、待澄清混在一个文件里，文件本身就是状态，不需要额外进度表。

结构不由散文约定，而由 `assets/req-model.schema.json` 定义——几段、每段由哪些块组成、每个表格必须有哪些列、每列承担什么语义、跨表要满足什么约束，全在那里。`req_lint.py` 读它做校验，脚本里没有任何段号和编号前缀。详见下文「输出契约」。

## When to Use

- 拿到 PRD / 需求单 / 技术设计，要先把「这次到底要验什么」定下来
- 多来源并存（需求文档 + 接口定义 + 代码 + 缺陷单），需要交叉核对、暴露矛盾
- 要判断这个需求**能不能测、值不值得自动化**
- 需求评审前，要一份能拿着逐条问的清单

## When NOT to Use

- **写测试用例** → 不在本 skill。本 skill 只到「要验什么」与「凭什么这么说」，不含操作步骤、测试数据、断言代码
- 定测试深度 / 排测试计划 → 不在本 skill
- 已确认缺陷的根因分析 → 不在本 skill
- 完全无文档且系统陌生 → 先探索，有了系统理解再回来分析

**本 skill 完全自包含**：不读、不引用其它 skill 的任何文件，单独安装即可完成全部工作。

## 四块产物

| # | 产物 | 回答什么 | 闸门拦什么 |
|---|---|---|---|
| 1 | 功能点 | 这次交付什么、**不交付什么** | 每个功能点 ≥ 1 条分析（E023）、≥ 1 条证据（E026） |
| 2 | 需求用例分析 | 每个功能点要验什么、在哪个维度找缺陷 | 维度必须在枚举内、验证意图 ≥ 12 字、判 C 必须写复核条件（E021） |
| 3 | 证据 | 每条结论凭什么，别人能不能自己核对 | 位置必须可定位（E024）、摘录必须是原句（E025） |
| 4 | 待澄清 | 还剩什么不确定、谁回答、答错影响谁 | 必须有责任人（E006）、必须有假设与后果 |
| 5 | 移交索引 | 下游要不要读全文 | 五个数字与实际条目对账（E014） |

★ 第 2 段是产物主体。它与「测试点清单」的区别：每行必须写清**在哪个维度找缺陷**，而全写正常流等于没分析——正常流只在实现完全缺失时失败，缺陷基本都在异常、边界、状态、权限里。

**编号规则**：`FP-01` 功能点、`TA-01` 分析项、`EVD-01` 证据、`OQ-01` 待澄清。全局唯一、不复用；删除的编号留空，否则下游引用会指错。

## 五条铁律

1. **没有证据的结论不进正文。** 每条功能点、分析项都要能被一条 `EVD-*` 支撑：位置可定位、摘录是原句。找不到出处的，不要写假设，写进待澄清。
2. **功能点是唯一挂载点。** 证据挂功能点或分析项，分析项挂功能点。挂不上的东西，说明它不属于这次范围，或者功能点切错了。
3. **分析写意图，不写步骤。** 「错误 4 次仍可登录、第 5 次返回 LOCKED」是意图；「打开登录页，输入账号，点击登录」是步骤，属于下游用例 skill。
4. **空要写明，不能留白。** 确实没有的，写「已核对，无此类要素」+ 依据。留白无法区分「没有」和「没查」——这是分析失效最常见的原因。
5. **不确定性必须落到人。** 每条待澄清写清「向谁确认 + 我的假设 + 若不成立的后果」。只写「待确认」三个字，等于把它留到明年。

## 来源分级与冲突裁决

| 标记 | 来源 | 证据强度 | 附加要求 |
|---|---|---|---|
| `SRC-API` | 接口定义文件（OpenAPI / proto / Postman） | 强 | — |
| `SRC-CODE` | 代码实现（`文件:行`） | 强 | 需记分支与 commit |
| `SRC-DOC` | 技术设计 / 库表设计 / 接入文档 | 中 | — |
| `SRC-REQ` | PRD / 需求单 | 中 | — |
| `SRC-TICKET` | 缺陷单 / 工单 | 弱 | 标注是否已修复 |
| `SRC-VERBAL` | 口头 / 群聊 / 会议口述 | 弱 | **必须同时挂待澄清** |

**冲突裁决分两类，不可混为一谈：**

- **「实际是什么」**——静态事实冲突以 `SRC-API` / `SRC-CODE` 为准（代码是运行时的真实行为）。
- **「应该是什么」**——以需求方裁决为准。**代码与需求不一致不是「以高优先级覆盖」，而是一条待确认的缺陷线索**，记入待澄清，绝不能在产物里悄悄抹平。

> 这条区别很关键：如果一律「以代码为准」，实现里的 bug 会被写进需求分析，然后下游全部当作预期行为。

## 输出契约

产物不只是给人读的。它要能被下游直接消费——按 `FP-*` 排计划、按 `TA-*` 生成用例、按维度分布判断覆盖倾向。靠正则刮一份散文式 Markdown 不可靠，所以结构必须先定下来。

契约在 `assets/req-model.schema.json`：5 段、5 张表/小节、34 个列定义、7 条跨表约束。每列声明一个 **role**，闸门按 role 校验，不按段写死规则：

| role | 校验什么 | 拦住的问题 |
|---|---|---|
| `id` | `<前缀>-<两位以上序号>`，全局唯一 | 编号写 `TA-3`、前缀张冠李戴、重复占号 |
| `source` | 必须含 `[SRC-*]`；含 `SRC-VERBAL` 的还要同行引用 `OQ-*` | 结论没有出处；口头需求被当成结论 |
| `ref` | 值必须是文档里真实存在的编号，支持一行多个（`、` 分隔） | `EVD-01` 挂到不存在的 `TA-99` |
| `enum` | 值 ∈ 声明集合（如 `正常流/边界/异常…`、`A/B/C`） | 维度写成「各种情况」、强弱写成「比较高」 |
| `locator` | 必须落到具体处所：`文件:行` / `§2.1` / `GET /api/login` | 位置只写「PRD」「文档」「代码」 |
| `quote` | 必须是原句片段，不能以「详见 / 同上 / 见第 X 章」开头 | 用指针冒充证据 |
| `person` | 非空且不是「待确认 / TBD / ?」 | 待澄清挂着但没人负责 |
| `text` | 非空、非破折号占位、满足 `min_len` | 必填格写 `—`；验证意图只写八个字 |
| `number` | 必须含数字 | 性能指标写成「很快」 |

有三件事散文写不出、只有 schema 能表达，也因此只有 schema 能机判：

1. **列的必备性。** 分析表少了「维度」这一列，和每行维度都空着，是两种不同的错。前者是结构违约（E012），后者是内容缺失（E017）。
2. **跨表约束。** 每个功能点都要有分析项（E023）和证据（E026）；判 C 的必须有复核条件（E021）。这些都没法落在单张表里。
3. **移交索引与实际条目的一致性。** 第 5 段那行 `A10/B3/C1` 是人手写的，改了一条分级它不会自动变。闸门去数实际条数（E014）——否则下游读到的是一份假数据。

约束在 schema 顶层声明，带 `on` 指明作用于哪些段（按 `key`，不按段号）：

```json
{ "name": "every_fp_has_evidence", "on": ["fp", "evidence"], "level": "E" }
```

脚本里没有出现任何段号，也没有出现任何编号前缀。列按 `tag` 定位（`automation` / `dimension` / `strength` / `oq_status`），改列名不影响校验。改结构只改 schema，脚本不动；把 schema 改坏（段号断了、key 重复、role 拼错、声明了脚本没实现的约束），脚本会以退出码 2 拒绝运行，不会带着坏结构继续判。

```bash
python3 scripts/req_lint.py --describe   # 按 schema 打印完整字段契约
```

## 工作流

### 阶段〇｜收料与定性

**先要这些东西，缺的先记下、不等：**

- 需求侧：PRD / 需求单 / 原型 / 验收标准
- 技术侧：技术设计、库表设计、接口定义（OpenAPI / proto）、时序图
- 实现侧：代码仓库（**必须记分支名 + commit hash 或拉取时间**）
- 历史侧：相似需求的旧分析、缺陷单、线上问题记录

**基线是硬要求。** 没有 commit 的产物三个月后无法判断是否还成立，也划不清「改动前 / 改动后」的边界。

收料结果决定产物性质，**这一步走错，后面全是白工**：

| 收到的材料 | 该做什么 | 不该做什么 |
|---|---|---|
| 有 PRD，或接口定义 / 代码 | 直接进阶段一，切功能点 | — |
| 只有口述，需求方可达 | 先出一页澄清清单（10~15 问，按影响面排序），澄清完再切功能点 | 不要先砌四段产物——假设越完整越像结论 |
| 只有口述，需求方不可达 | 切功能点，全部标 `SRC-VERBAL` 并逐条挂待澄清，文件头注明「待确认草案，不可作为验收依据」 | 不要自行拟一套行业基线当结论 |

材料缺哪块，就在待澄清里记一条「缺 X，影响第 N 段，向 A 索取」，然后继续——不要因为缺材料停工，也不要因为缺材料就跳过那一段。

### 阶段一｜切功能点

按「用户能描述出来的一段行为」切。两个纪律：

- **切到能被独立验收的粒度。** 一个功能点对应一句话能说清的用户可见行为；写不出用户可见行为的，说明它还是实现细节，不是功能点。
- **同时写「本期不做」。** 功能点的补集就是范围边界。不写，范围会在联调期被逐条追加。

### 阶段二｜逐点分析

对每个功能点，把可用的分析维度过一遍，不是想起来才查：

正常流 → 边界 → 异常 → 状态 → 权限 → 并发 → 幂等 → 时序 → 数据一致性 → 兼容 → 性能

不是每个维度都要填，但**没填的要能说清为什么**。加载 `references/testability-grading.md` 判断每条能不能自动化：

- **A**：能机器判定，且能常驻 CI
- **B**：能机器判定，但依赖不稳定环境或需要构造
- **C**：当前无法机器判定——必须写清什么条件下重评，否则半年后会有人重评一遍

每条分析写「验证意图 + 关键取值 + 观测点」三件套。观测点写不出具体位置的（接口字段 / DB 字段 / 日志 / 埋点），说明这条还没到可执行状态。

### 阶段三｜建证据台账

加载 `references/ambiguity-patterns.md`，按八类模式逐类过筛材料，三类冲突分别处理：

| 冲突类型 | 例子 | 落到哪 |
|---|---|---|
| 文档内自相矛盾 | PRD 第 3 章说必填、第 7 章说选填 | 待澄清 |
| 跨文档冲突 | PRD 与接口文档字段类型不一致 | 待澄清 |
| 文档 vs 实现 | 代码允许的状态迁移，需求文档未提 | 功能点补录 + 待澄清确认「是否预期」 |

每写一条证据，都要能回答：**换个人拿着「位置 + 摘录」，能不能自己核对？** 回答不了就不是证据。

扫描的目标不是把矛盾消灭，而是**把矛盾变成一条能被回答的问题**。

### 阶段四｜澄清（⏸ 检查点，不代答）

- 一次问完，按影响面排序（影响结论多的先问）
- 每条给出「我的假设 + 若成立的影响 + 若不成立的影响」，让对方容易回答
- 拿到裁决写回「状态」列并注明裁决人与日期
- **无人在场（headless / CI）时**：全部保留为未裁决，取保守分支继续，并在文件头标注「基于假设 X，待确认」。不许伪造裁决

### 阶段五｜闸门与移交

```bash
python3 scripts/req_lint.py {项目}/需求测试分析.md
```

退出码 **1** 即不可交付，按报错逐条修，不要绕过。退出码 **2** 说明输入或 schema 本身有问题（文件读不到、schema 写坏），不是产物的问题。

想先看清结构要求再动笔：`python3 scripts/req_lint.py --describe`。想确认闸门本身没坏：`python3 scripts/selftest_req.py`。

移交时给一句话索引，方便下游直接判断要不要读全文：

```
需求测试分析.md · 5 个功能点 · 14 条分析 · 7 条证据 · 3 个待澄清（0 已裁决）· 自动化 A10/B3/C1 · 基线 feat/login@a1b2c3d
```

这行由闸门对账（E014）：写的数字与实际条目不符会直接报错。

## Common Mistakes

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 先砌四段产物，再补证据 | 假设越完整越像结论，评审时无人能分辨哪条是猜的 | 材料不足时先出澄清清单，不要产出看似完整的文档 |
| 把「待确认」写进正文当结论 | 下游基于假设写用例，全量返工 | 正文只留有证据的；模糊项进待澄清 |
| 证据位置写「PRD」或「见文档」 | 无法核对，等于没有证据 | 写到 `§2.1` / `文件:行` / `GET /path` |
| 摘录写「详见第 3 章」 | 用指针冒充证据，下游无法判真假 | 抄原句，哪怕只有半句 |
| 只写正常流 | 正常流只在实现完全缺失时失败，缺陷全漏 | 每条功能点至少补一条异常 / 边界 / 状态 / 权限 |
| 分析写成操作步骤 | 与用例重复，且步骤一改就要重写 | 写「前置 X → 期望 Y」，不写点击与输入 |
| 功能点切到实现粒度 | 断言只能落在代码上，无法验收 | 切到「用户能描述出来的一段行为」 |
| 不写「本期不做」 | 范围在联调期被逐条追加 | 功能点的补集要显式列出 |
| 只写「待确认」，不写向谁确认 | 问题永远没人答 | 每条必须有责任人、假设、后果 |
| 判 C 不写复核条件 | 半年后有人重新评估一遍 | 写明不能自动化的具体障碍 |
| 有代码就「以代码为准」 | 实现里的 bug 变成「预期行为」 | 静态事实以代码为准；应然以需求方裁决为准 |
| 改了分级但没改移交索引 | 下游只读那一行，读到的是假数据 | 闸门 E014 会对账，改完重跑一次 |
| 随手改表头列名 | 闸门按 tag/列名定位，改名即判缺列 | 改结构先改 schema，再同步模板 |

## 与其它 skill 的关系

本 skill 只做一件事：把需求变成「要验什么 + 凭什么这么说」。

**下游是写用例的 skill**——它拿 `FP-*` 排计划、拿 `TA-*` 展开步骤与数据、拿 `EVD-*` 回查预期值是否与原文一致、拿 `OQ-*` 标注哪些用例暂不可定稿。因此本文件刻意不写步骤：写了就与用例重复，且一改就要改两处。

产物是纯 Markdown、纯文本表格，不依赖任何脚本或配置文件即可阅读。若宿主里同时装了本合集其它 skill，产物可直接作为它们的输入；但**本 skill 不引用它们的任何文件**，单独安装同样完整可用。
