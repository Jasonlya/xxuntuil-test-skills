## 什么时候用它

**用**：

- 拿到 PRD / 需求单 / 技术设计，要在写用例之前把「这次到底要验什么」定下来
- 多来源并存（需求文档 + 接口定义 + 代码 + 缺陷单），要交叉核对、暴露矛盾
- 需求评审前，要一份能拿着逐条问的清单
- 要判断这个需求**能不能测、值不值得自动化**
- 只拿到一句口述，需要把它变成一份「待确认草案」而不是一份看着完整的假文档

**不用**：

- 写测试用例 —— 这里只到「要验什么」，不含操作步骤、测试数据、断言代码
- 定测试深度、排测试计划
- 已确认缺陷的根因分析
- 完全无文档且系统陌生 —— 先探索，有系统理解再回来分析

## 它和「测试点清单」差在哪

测试点清单的问题不是不够多，而是**没法验证**：写完没人能判断是否完整，也没人知道某一条从哪来，于是评审变成互相念稿。

三样东西把清单变成可验证的产物：

| 加什么 | 解决什么 | 没有它会怎样 |
|---|---|---|
| **功能点** | 范围可数：几个点、各自优先级、哪些不做 | 范围在联调期被逐条追加，没人说得清「做完了」是什么状态 |
| **证据** | 每条结论能落到原文位置与原句，第三人可独立核对 | 结论依赖分析者的记忆；三个月后无法判断还成不成立 |
| **待澄清** | 不确定的部分显式化，带责任人、假设与后果 | 假设混在正文里看起来像结论，下游照着它写用例，全量返工 |

一句话：**这个 skill 不保证你写对了，它保证你写的东西能被别人查。**

## 四块产物

| # | 产物 | 回答什么 | 闸门拦什么 |
|---|---|---|---|
| 1 | 功能点 | 这次交付什么、**不交付什么** | 每个功能点 ≥ 1 条分析（E023）、≥ 1 条证据（E026） |
| 2 | 需求用例分析 | 每个功能点要验什么、在哪个维度找缺陷 | 维度在枚举内、验证意图 ≥ 12 字、判 C 必须有复核条件（E021） |
| 3 | 证据 | 每条结论凭什么，别人能不能自己核对 | 位置可定位（E024）、摘录必须是原句（E025） |
| 4 | 待澄清 | 还剩什么不确定、谁回答、答错影响谁 | 必须有责任人（E006）、必须有假设与后果 |
| 5 | 移交索引 | 下游要不要读全文 | 五个数字与实际条目对账（E014） |

第 2 块是主体。它和「测试点」的区别只有一条：**每行必须写清在哪个维度找缺陷。** 十一个维度是：正常流、边界、异常、状态、权限、并发、幂等、时序、数据一致性、兼容、性能。

全写正常流等于没分析——正常流只在实现完全缺失时失败，缺陷基本都在异常、边界、状态、权限里。这条判断闸门也做：全部分析项的维度都是正常流时，报 W012。

**编号**：`FP-01` 功能点、`TA-01` 分析项、`EVD-01` 证据、`OQ-01` 待澄清。全局唯一、不复用；删除的编号留空，否则下游引用会指错。

## 分析写到什么粒度

分界线只有一条：**写意图，不写步骤。**

| | 写法 | 为什么 |
|---|---|---|
| ❌ 写成用例 | 打开登录页 → 输入账号 → 输入错误密码 → 点击登录 → 断言提示「密码错误」 | 这是下游用例 skill 的活；写了就与它重复，且步骤一改要改两处 |
| ✅ 写成意图 | 密码错误 → 401，且「账号存在+错密码」与「账号不存在」返回逐字相同的 code 与 message | 一改数据就能变成多条用例，且断言点唯一 |

每行还要给两列：**关键取值**（决定结论的取值或阈值，如「错误次数 4/5」「长度 8/20/21」，只写「各种情况」等于没写）和**观测点**（具体到接口字段 / DB 字段 / 日志 / 埋点，不能只写「接口」「页面」）。

自动化判 A / B / C，判定顺序刻意设计成**先判能否机判、再判能否常驻**：

```
① 结果能不能机判？           不能 → C，且必须写复核条件
② 能机判且满足全部常驻条件？   是 → A
③ 能机判但有一项不满足        → B
```

多数人从 A 开始判，结果把不稳定用例全塞进 A，三个月后流水线红得没人看。反过来从 C 开始判，才能守住「不能机判的东西不该进 CI」。

可测性四问（OBS / CTRL / ENV / TIME）没有单独一张表，它们是填四列的口径：OBS 落到观测点列，TIME 落到关键取值列，CTRL 与 ENV 落到自动化与复核条件列。单独列一张四问表，会得到一份看起来严谨、但和后面的分析项对不上的附录。详见 [`references/testability-grading.md`](./references/testability-grading.md)。

## 证据写到什么程度

一条证据 = **位置 + 原句 + 强度**。三者缺一，它就不是证据。

| | 写法 | 闸门 |
|---|---|---|
| ❌ 只有载体 | 位置写「PRD」、写「文档」、写「代码」 | E024 |
| ❌ 用指针冒充 | 摘录写「详见第 3 章」「同上」「参见接入文档」 | E025 |
| ❌ 转述 | 摘录写「需求里说连续输错会锁定」 | 不拦，但强度只能是弱 |
| ✅ 原句 | 位置 `PRD §3.1`，摘录「连续输错 5 次锁定 30 分钟，到期自动解锁」 | 通过 |
| ✅ 代码 | 位置 `auth/lock.go:88-104`，摘录 `if user.FailCount >= 5 { ... }` | 通过 |

强度与来源类型联动：`SRC-API` / `SRC-CODE` 是**强**（运行时的真实行为），`SRC-REQ` / `SRC-DOC` 是**中**，`SRC-TICKET` / `SRC-VERBAL` 是**弱**。口头来源除了是弱证据，还必须同行挂一条待澄清（E011），因为「某某口头说了」在三个月后无法验证。

强证据占比低于 30% 时闸门报 W013——这不是格式问题，是提醒：**这份产物目前的结论主要建立在文档转述和口头上。**

**冲突裁决分两类，不可混为一谈：** 「实际是什么」以 `SRC-API` / `SRC-CODE` 为准；「应该是什么」以需求方裁决为准。两者不一致**不是「以高优先级覆盖」，而是一条待确认的缺陷线索**。如果一律「以代码为准」，实现里的 bug 会被写进产物，然后一路下游被当作预期行为。

## 输出契约（schema）

产物要能被下游消费——按 `FP-*` 排计划、按 `TA-*` 生成用例、按维度分布判断覆盖倾向。让下游用正则刮散文式 Markdown 是不可靠的，所以结构先定死。

[`assets/req-model.schema.json`](./assets/req-model.schema.json) 定义 5 段、5 个块、34 个列、7 条跨表约束。每列声明一个 **role**，闸门按 role 通用校验：

| role | 校验什么 | 拦住的问题 |
|---|---|---|
| `id` | `<前缀>-<两位以上序号>`，全局唯一 | 编号写 `TA-3`、前缀张冠李戴、重复占号 |
| `source` | 必须含 `[SRC-*]`；含 `SRC-VERBAL` 的还要同行引用 `OQ-*` | 结论没有出处；口头需求被当成结论 |
| `ref` | 指向的编号必须真实存在，支持一行多个（`、` 分隔） | `EVD-01` 挂到不存在的 `TA-99` |
| `enum` | 值 ∈ 声明集合（维度、`A/B/C`、`强/中/弱`、`P0/P1/P2`） | 维度写「各种情况」、强度写「比较高」 |
| `locator` | 必须落到具体处所：`文件:行` / `§2.1` / `GET /api/login` | 位置只写「PRD」「文档」「代码」 |
| `quote` | 必须是原句片段，不能以「详见 / 同上 / 见第 X 章」开头 | 用指针冒充证据 |
| `person` | 非空，且不是「待确认 / TBD / ?」 | 待澄清挂着但没人负责 |
| `text` | 非空、非破折号占位、满足最小长度 | 必填格写「—」；验证意图只写八个字 |
| `number` | 必须含数字 | 性能指标写成「很快」 |
| `any` | 只查非空（若必需） | — |

三件散文写不出、只有 schema 能机判的事：

1. **列的必备性** —— 分析表少了「维度」这一列（E012，结构违约）和每行维度都空着（E017，内容缺失）是两种错，修法完全不同。
2. **跨表约束** —— 每个功能点都要有分析项（E023）和证据（E026）；判 C 的必须有复核条件（E021）。
3. **移交索引的一致性** —— 第 5 段那行 `A11/B2/C0` 是人手写的，改了一条分级它不会自动变。schema 声明了这行的格式，闸门就去数实际条数（E014），否则下游读到的是一份假数据。

约束在 schema 顶层声明，带 `on` 指明作用于哪些段（按 `key`，不按段号）：

```json
{ "name": "every_fp_has_evidence", "on": ["fp", "evidence"], "level": "E" }
```

**脚本里没有任何段号，也没有任何编号前缀。** 需要定位时按 section key 查，列按 `tag` 定位（`automation` / `dimension` / `strength` / `oq_status`）——改列名不影响校验。改结构只改 schema，脚本不动。schema 被改坏（段号断了、key 重复、role 拼错、声明了脚本没实现的约束）时，以退出码 **2** 拒绝运行，不会带着坏结构继续判。

```bash
python3 scripts/req_lint.py --describe   # 按 schema 打印完整字段契约
```

## 产物长什么样

从模板里截两段（完整示例见 [`assets/req-model-template.md`](./assets/req-model-template.md)，是一个登录需求）：

```markdown
| 编号 | 功能点 | 维度 | 验证意图 | 关键取值 | 观测点 | 自动化 | 复核条件 | 来源 |
|---|---|---|---|---|---|---|---|---|
| TA-02 | FP-01 | 异常 | 密码错误 → 401，且「账号存在+错密码」与「账号不存在」返回逐字相同的 code 与 message | 未知账号 / 已知账号+错密码 | 响应 body.code、body.message | A | — | [SRC-REQ] PRD §2.1 |
| TA-14 | FP-02 | 兼容 | 短信通道返回失败时，用户可见结果与「验证码错误」可区分 | 通道超时 / 通道 5xx | 响应 code 与前端提示文案 | C | 接入真实通道或稳定挡板后重评 | [SRC-REQ] PRD §2.2.6 |
```

```markdown
| 编号 | 支撑对象 | 来源类型 | 位置 | 原文摘录 | 强度 |
|---|---|---|---|---|---|
| EVD-02 | FP-03、TA-08、TA-09 | SRC-REQ | PRD §3.1 | 「连续输错 5 次锁定 30 分钟，到期自动解锁」 | 强 |
| EVD-03 | FP-03、TA-10 | SRC-CODE | auth/lock.go:88-104 | `if user.FailCount >= 5 { user.LockUntil = now.Add(30 * time.Minute) }` | 强 |
```

一条证据可以同时支撑多条结论（`、` 分隔）。挂到功能点上的证据，自动覆盖该功能点下的全部分析项——只有「分析项自己没证据、所属功能点也没证据」才算真缺口（W011）。

## 五阶段工作流

| 阶段 | 做什么 | 关键纪律 |
|---|---|---|
| 〇 收料 | 清点 PRD / 技术设计 / 接口定义 / 代码 / 缺陷单，**记基线** | **收料结果决定产物性质**，这一步走错后面全是白工 |
| 一 切功能点 | 按「用户能描述出来的一段行为」切，同时写「本期不做」 | 多切出来的都是分析方的发明 |
| 二 逐点分析 | 十一个维度过一遍，判 A/B/C | 先证明能测，再讨论自动化；判 C 必须写复核条件 |
| 三 建证据台账 | 八类歧义模式逐类过筛，三类冲突分别处理 | 目标不是消灭矛盾，是把矛盾变成**能被回答的问题** |
| 四 澄清 ⏸ | 一次问完，按影响面排序 | 无人在场时全部保留未裁决，取保守分支并标注，**不许伪造裁决** |
| 五 闸门与移交 | 跑 `req_lint.py` | 退出码 1 不可交付 |

阶段〇 的三分支判断，是这个 skill 与「先砌文档」的分界线：

| 收到的材料 | 该做什么 | 不该做什么 |
|---|---|---|
| 有 PRD，或接口定义 / 代码 | 直接切功能点 | — |
| 只有口述，需求方可达 | 先出一页澄清清单（10~15 问，按影响面排序），澄清完再切 | **不要先砌四块产物**——假设越完整越像结论 |
| 只有口述，需求方不可达 | 切功能点，全部标 `SRC-VERBAL` 并逐条挂待澄清，文件头注明「待确认草案」 | 不要自行拟一套行业基线当结论 |

**八类歧义模式**（见 [`references/ambiguity-patterns.md`](./references/ambiguity-patterns.md)）：量词与范围缺失、时间边界模糊（必须双侧）、角色重叠与自审自批、状态与终态遗漏、数据来源与缺失值语义、失败语义与回滚、权限与可见性混谈、口径不一致。每类都给了可直接复制的问法。

## 闸门

```bash
python3 scripts/req_lint.py {项目}/需求测试分析.md
python3 scripts/req_lint.py {项目}/需求测试分析.md --json
python3 scripts/req_lint.py --describe        # 打印输出契约
python3 scripts/selftest_req.py               # 自测闸门本身
```

**23 项 E 级（退出码 1 阻断）**：

| 码 | 拦什么 |
|---|---|
| E001 | 缺段 |
| E002 | 段内容为空（空段必须写「已核对，无此类要素」） |
| E003 | 编号条目缺来源标注 |
| E004 | 状态缺非法迁移（保留码位，v2 用「维度=状态」表达） |
| E005 | 接口缺失败态（保留码位，v2 用「维度=异常」表达） |
| E006 | 待澄清缺「向谁确认」，或只写「待确认」 |
| E007 | 出现不可判定表述（功能正常 / 符合预期 / 表现良好…） |
| E008 | 非功能指标无数值（保留码位，v2 用「维度=性能」表达） |
| E009 | 分析项的观测点为空 |
| E010 | 自动化分级不在 A/B/C 之内 |
| E011 | 出现 `SRC-VERBAL` 但未在同一行引用待澄清编号 |
| E012 | 缺 schema 要求的必需列 |
| E013 | 缺 schema 要求的必需块（表格 / 小节 / 代码块） |
| E014 | 移交索引里的条数与实际不符 |
| E015 | 引用指向不存在的编号 |
| E016 | 编号格式不符（前缀错 / 序号不足两位 / ref 里混了非编号） |
| E017 | 必填单元格为空（含只写「—」） |
| E018 | 枚举值不在允许范围内 |
| E019 | 表格行数少于 schema 要求 |
| E020 | 小节列表项少于 schema 要求 |
| E021 | 判 C 却没写复核条件 |
| E022 | 必需文本过短，通常是「正常」「符合要求」这类不成句内容 |
| E023 | 功能点没有任何分析项 |
| E024 | 证据位置只有载体没有位置（写「PRD」「文档」「代码」） |
| E025 | 原文摘录是指代而非原句（写「详见」「同上」） |
| E026 | 功能点没有任何证据支撑 |

**12 项 W 级（仅提示，不阻断）**：W001 表格超 40 行 · W002 待澄清超 10 条 · W003 缺基线 · W004 编号重复 · W006 段标题偏离 · W007 声明为空但 schema 要求有内容 · W008 表格有 schema 未定义的列 · W009 列顺序与 schema 不一致 · W010 移交索引无法解析 · W011 分析项及其功能点都无证据 · W012 全部分析都是正常流维度 · W013 强证据占比低于 30%。

## 安装与使用

```bash
# 从合集仓库安装（单装即可，不依赖其它 skill）
git clone https://github.com/Jasonlya/xxuntuil-test-skills.git
cp -R xxuntuil-test-skills/skills/requirement-analysis ~/.workbuddy/skills/

# 或者用仓库脚本
./install.sh requirement-analysis
```

装完重启宿主，说「分析一下这个需求」「帮我做需求评审」「这个需求怎么测」即可触发。

产出物是单个 `{项目}/需求测试分析.md`，纯 Markdown 表格，不装任何工具也能读。功能点、分析、证据、待澄清都在这一个文件里——文件本身就是状态，不需要额外进度表。

| Python 版本兼容 | 只用标准库；`from __future__ import annotations`，3.8+ 可用 |

自测的做法是**单点破坏**：每次只改一处，断言命中的码集合与预期完全一致——多一条少一条都算失败。只证明「模板能过」没有意义，一个永远返回 0 的脚本也能过。

一次删掉 FP-01 的四条分析项，触发的是连锁错误而不是一条：E023（功能点无分析）+ 两条 E015（证据与待澄清指向已删编号）+ 一条 E014（索引仍写 14 条分析，实际 10 条）。这类连锁正是「结构里有交叉引用」的价值。

不写进表里的：没有做「有 skill vs 无 skill」的产出质量对照，所以这里不出现「效率提升 X%」「缺陷发现率提升 Y%」这类数字。也没有测人工手写耗时。

## 已知边界

- **只判结构，不判内容正确性。** 闸门能判定「这条结论有没有证据」「这个功能点有没有分析」，判不了「这条分析是不是真正该验的」。结构合规的产物仍然可能是错的。
- **schema 定的就是验收口径。** 加一列、改列名、放宽某个枚举，等于改了「什么算合格」，必须同步模板与下游消费方；否则产物合法了，下游解析会断。
- **不替代需求评审。** 它把矛盾整理成问题清单，但问题得有人答。
- **八类歧义模式是经验清单，不是穷举。** 命中不了不代表没歧义，只是这八类没扫出来。
- **基线变化后产物需复核。** 代码大改（尤其状态机、接口契约）后，功能点与证据必须重新核对，否则产物会悄悄过期。
- **不做跨需求汇总。** 一个需求一份产物，不做需求间的依赖分析。
- **不生成用例。** 这是刻意的：产物只到「要验什么」，步骤、数据、断言代码交给下游用例 skill，避免一处改动要改两处。
