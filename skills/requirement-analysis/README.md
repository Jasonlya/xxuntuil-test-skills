> 把一份需求变成离开文档后仍能被独立验证的模型：每条结论带来源，每条规则判可测性，每个可测项定自动化级别。

## 什么时候用它

**用**：

- 拿到 PRD / 需求单 / 技术设计，要在写用例之前先把「到底要做什么」定下来
- 多来源并存（需求文档 + 接口定义 + 代码 + 缺陷单），要交叉核对、暴露矛盾
- 需求评审前，要一份能拿着逐条问的清单
- 要判断这个需求**值不值得自动化、能自动化到什么程度**

**不用**：

- 写测试用例 —— 这里只输出「系统是什么」，不输出「怎么测」
- 定测试深度、测哪些类型 —— 那是策略的事
- 已确认缺陷的根因分析
- 完全无文档且系统陌生 —— 先探索，有系统理解再回来建模

## 它和「泛需求分析」差在哪

普通需求建模到「理解需求」就停下了，产出是一份结构化的描述。这个 skill 多走两步，因为**角色是测试开发工程师，不是业务分析师**：

**第一步：可测性四问。** 每条业务规则必须回答四件事，答不全就算不可测：

| 问 | 要答什么 | 为什么必须问 |
|---|---|---|
| OBS 观测点 | 结果在哪看：接口字段 / DB 字段 / 消息 / 日志 / UI | 写不出观测点的规则，在当前架构下就是不可验证的规则 |
| CTRL 可控性 | 前置状态能不能造、怎么造、造一次多久 | 「造一次等 3 天」和「3 秒」在自动化上是两个世界 |
| ENV 环境依赖 | 依赖哪些服务、真实还是挡板、能否独占 | 依赖在 CI 里经常超时 → 这条最多只能到 B 级 |
| TIME 时序 | 是否依赖等待、轮询、定时任务、跨天 | 「等 30 秒看看」不是时序可控，那是不稳定的 sleep |

**第二步：自动化 A/B/C 分级。** 判定顺序刻意设计成**先判能否机判、再判能否常驻**：

```
① 结果能不能机判？           不能 → C
② 能机判且满足全部常驻条件？   是 → A
③ 能机判但有一项不满足        → B
```

多数人从 A 开始判，结果把不稳定用例全塞进 A，三个月后流水线红得没人看。反过来从 C 开始判，才能守住「不能机判的东西不该进 CI」这条线。

**判 C 必须写清障碍**，而且要写「复核条件」——把「以后再说」变成一个可触发的条件：

```
AUTO-07｜REQ-05 退款到账通知｜C｜障碍：依赖真实支付渠道回调，测试环境无沙箱，
仅能生产小额实付验证；每次 1 人时｜复核条件：接入支付沙箱后重评为 B
```

## 十二段模型

| # | 段名 | 必须回答 | 闸门检查 |
|---|---|---|---|
| 1 | 目标与非目标 | 一句话目标 + 可量化成功标准 + 明确不做什么 | 非目标 ≥ 1 条 |
| 2 | 角色与权限 | 角色 × 能做 / 不能做 / 可见范围 | 每条带来源 |
| 3 | 状态与迁移 | 状态清单 + 合法迁移 + **非法迁移** | 每状态 ≥ 1 条非法迁移 |
| 4 | 数据契约 | 字段 × 类型 / 必填 / 边界 / 来源 / 校验时机 | `FLD-*` + 来源 |
| 5 | 接口与依赖 | 接口 × 成功态 / **失败态** / 超时 / 重试 / 幂等 | `API-*` + 失败态非空 |
| 6 | 业务规则 | 能被独立判定真假的陈述 | `REQ-*` + 来源 |
| 7 | 异常与降级 | 异常场景 → 系统行为 → 用户可见结果 | `EX-*` + 来源 |
| 8 | 非功能约束 | 指标 + **数值** + 测量方法 | `NFR-*` + 含数字 |
| 9 | 可测性评估 ★ | 观测点 / 可控性 / 环境 / 时序 | `TST-*` + 观测点非空 |
| 10 | 自动化分级 ★ | A / B / C + 理由 + 成本 | 值 ∈ {A,B,C} |
| 11 | 未决项 | 问题 + **向谁确认** + 影响 + 裁决 | `OQ-*` + 责任人 |
| 12 | 验证边界与移交 | 验什么 / **不验什么及理由** | 非空 |

★ 两段是本 skill 的分界线。

## 输出契约（schema）

模型要能被下游消费——按 `REQ-*` 写用例、按 `TST-*` 挑可自动化项、按 `AUTO-*` 排优先级。让下游用正则去刮散文式 Markdown 是不可靠的，所以结构先定死：

[`assets/req-model.schema.json`](./assets/req-model.schema.json) 定义 12 段、13 张表、6 个小节、1 个代码块、69 个列。每列声明一个 **role**，闸门按 role 通用校验，而不是按段写死规则：

| role | 校验什么 |
|---|---|
| `id` | `<前缀>-<两位以上序号>`，全局唯一 |
| `source` | 必须含 `[SRC-*]`；含 `SRC-VERBAL` 的还要同行引用 `OQ-*` |
| `ref` | 指向的编号必须真实存在，前缀在允许范围内 |
| `enum` | 值 ∈ 声明集合（`是/否/条件`、`A/B/C`、`已裁决/未裁决`） |
| `number` | 必须含数字 |
| `person` | 非空，且不是「待确认 / TBD / ?」 |
| `text` | 非空、非破折号占位、满足最小长度 |
| `any` | 只查非空（若必需） |

三件散文写不出、只有 schema 能机判的事：

1. **列的必备性** —— 第 5 段少了「失败态」列（E012，结构违约）和每行失败态都空着（E005，内容缺失）是两种错。
2. **跨表约束** —— 每个 `ST-*` 要有对应非法迁移（E004）；可测项条数与分级条数要对齐（W005）。
3. **移交索引的一致性** —— 第 12 段那行 `A4/B2/C1` 是人手写的，改了分级它不会自动变。schema 声明了这行的格式，闸门就去数实际条数（E014），否则下游读到的是一份假数据。

```bash
python3 scripts/req_lint.py --describe   # 按 schema 打印完整字段契约
```

改结构只改 schema，脚本不动。schema 被改坏（段号断了、role 拼错、约束引用不存在的名字）时，脚本以退出码 **2** 拒绝运行，不会带着坏结构继续判。

## 模型长什么样

从模板里截一段真实内容（完整示例见 [`assets/req-model-template.md`](./assets/req-model-template.md)，是一个优惠券下单抵扣的需求）：

```markdown
## 3. 状态与迁移

| 编号 | 状态 | 含义 | 终态 | 来源 |
|---|---|---|---|---|
| ST-01 | UNUSED | 已领取未使用 | 否 | [SRC-REQ §4.1] |
| ST-03 | USED   | 已抵扣核销   | 是 | [SRC-REQ §4.1] |

**非法迁移（必须写拦截方式）**

| 从 | 尝试 | 期望 | 拦截方式 | 来源 |
|---|---|---|---|---|
| ST-03 | 再次锁定 | 拒绝 | 返回 code=40901，券状态不变 | [SRC-CODE CouponService.java:212] |
| ST-01 | 跳过锁定直接核销 | 拒绝 | 核销接口校验必须为 LOCKED，返回 40905 | [SRC-CODE CouponService.java:230] |
```

为什么非法迁移比合法迁移更重要：主链路的需求文档通常写得清楚，**异常出口基本不写**。而线上问题绝大多数发生在「本不该发生的流转发生了」。

## 六阶段工作流

| 阶段 | 做什么 | 关键纪律 |
|---|---|---|
| 〇 收料 | 清点 PRD / 技术设计 / 接口定义 / 代码 / 缺陷单 | **必须记基线**：分支 + commit。没基线的模型三个月后无法判断是否还成立 |
| 一 建模 | 按十二段填 | 先填指得到来源的，指不到的**不要编** |
| 二 冲突与歧义扫描 | 八类模式逐类过筛 | 目标不是消灭矛盾，是把矛盾变成**能被回答的问题** |
| 三 可测性与分级 ★ | 四问 + A/B/C | 先证明能测，再讨论自动化；判 C 必须写障碍 |
| 四 澄清 ⏸ | 一次问完，按影响面排序 | 无人在场时全部保留未裁决，取保守分支并标注，**不许伪造裁决** |
| 五 闸门与移交 | 跑 `req_lint.py` | 退出码 1 不可交付 |

**八类歧义模式**（见 [`references/ambiguity-patterns.md`](./references/ambiguity-patterns.md)）：量词与范围缺失、时间边界模糊（必须双侧）、角色重叠与自审自批、状态与终态遗漏、数据来源与缺失值语义、失败语义与回滚、权限与可见性混谈、口径不一致。每类都给了可直接复制的问法。

## 闸门

```bash
python3 scripts/req_lint.py {项目}/需求模型.md
python3 scripts/req_lint.py {项目}/需求模型.md --json
python3 scripts/req_lint.py --describe        # 打印输出契约
python3 scripts/selftest_req.py               # 自测闸门本身
```

**22 项 E 级（退出码 1 阻断）**：

| 码 | 拦什么 | 来源 |
|---|---|---|
| E001 | 缺段（十二段任一缺失） | |
| E002 | 段内容为空（空段必须写「已核对，无此类要素」） | |
| E003 | 编号条目缺来源标注 | |
| E004 | 状态缺对应的非法迁移 | |
| E005 | 接口缺失败态 | |
| E006 | 未决项缺「向谁确认」，或只写「待确认」 | |
| E007 | 出现不可判定表述（功能正常 / 符合预期 / 表现良好…） | |
| E008 | 非功能约束的数值列为空或不含数字 | |
| E009 | 可测性条目的观测点为空 | |
| E010 | 自动化分级不在 A/B/C 之内 | |
| E011 | 出现 `SRC-VERBAL` 但未在同一行引用未决项编号 | |
| E012 | 缺 schema 要求的必需列 | schema |
| E013 | 缺 schema 要求的必需块（表格 / 小节 / 代码块） | schema |
| E014 | 移交索引里的条数与实际不符 | schema |
| E015 | 引用指向不存在的编号 | schema |
| E016 | 编号格式不符（前缀错 / 序号不足两位） | schema |
| E017 | 必填单元格为空（含只写「—」） | schema |
| E018 | 枚举值不在允许范围内 | schema |
| E019 | 表格行数少于 schema 要求 | schema |
| E020 | 小节列表项少于 schema 要求 | schema |
| E021 | 判 C 却没写复核条件 | schema |
| E022 | 必需文本过短，通常是「正常」「符合要求」这类不成句内容 | schema |

**10 项 W 级（仅提示，不阻断）**：W001 表格超 40 行 · W002 未决项超 10 条 · W003 缺基线 · W004 编号重复 · W005 可测项多于分级项 · W006 段标题偏离 · W007 声明为空但 schema 要求有内容 · W008 表格有 schema 未定义的列 · W009 列顺序与 schema 不一致 · W010 移交索引无法解析。

有两处设计值得单独说：

**E011 强制口头来源落成待确认项。** 规则标注 `[SRC-VERBAL]` 时必须同行引用一个 `OQ-*`，否则报错。因为「某某口头说了」不是可追溯的来源，它在三个月后无法验证——所以必须在建模阶段就把它转成一条有责任人的问题。

**冲突裁决分两类。** 「实际是什么」以代码 / 接口定义为准；「应该是什么」以需求方裁决为准。**两者不一致不是「以高优先级覆盖」，而是一条待确认的缺陷线索。** 如果一律「以代码为准」，实现里的 bug 会被写进模型，然后一路下游被当作预期行为。

## 安装与使用

```bash
# 从合集仓库安装（单装即可，不依赖其它 skill）
git clone https://github.com/Jasonlya/xxuntuil-test-skills.git
cp -R xxuntuil-test-skills/skills/requirement-analysis ~/.workbuddy/skills/

# 或者用仓库脚本
./install.sh requirement-analysis
```

装完重启宿主，说「分析一下这个需求」「帮我做需求建模」「这个需求能不能自动化」即可触发。

产出物是单个 `{项目}/需求模型.md`，纯 Markdown 表格，不装任何工具也能读。模型、未决项、裁决都在这一个文件里——文件本身就是状态。结构同时被 schema 约束，所以下游脚本也能直接按 `REQ-*` / `TST-*` / `AUTO-*` 定位条目，不用刮正则。

## 实测记录

2026-11-26，本地 macOS + Python 3.13：

| 检查 | 结果 |
|---|---|
| 模板 `assets/req-model-template.md` | **E 0 · W 0**，退出码 0 |
| `scripts/selftest_req.py` | **34 个单点破坏 + 9 个坏 schema 用例全部符合预期**，退出码 0 |
| 错误码覆盖 | 脚本声明 32 个码（22 E + 10 W），自测用例覆盖 32 个，无「写了但永不触发」的检查项 |
| 坏 schema | 10 类（缺段 / 段号重复 / role 拼错 / 枚举缺 values / 约束未定义 / 缺 columns / id_prefix 无 id 列 / 代码块缺 must_contain / JSON 语法坏 / 文件不存在）一律退出码 2，无静默放行 |
| Python 版本兼容 | 只用标准库；`from __future__ import annotations`，3.8+ 可用 |

自测的做法是**单点破坏**：每次只改一处，断言命中的码集合与预期完全一致——多一条少一条都算失败。只证明「模板能过」没有意义，一个永远返回 0 的脚本也能过。

不写进表里的：没有拿真实项目的需求跑过对照实验，所以这里不出现「效率提升 X%」这类数字。

## 已知边界

- **只判结构，不判内容正确性。** 闸门能判定「这条规则有没有来源」「这个状态有没有非法迁移」，判不了「这条规则是不是需求方真正想要的」。结构合规的模型仍然可能是错的。
- **schema 定的就是验收口径。** 加一列、改列名、放宽某个枚举，等于改了「什么算合格」，必须同步模板与下游消费方；否则模型合法了，下游解析会断。
- **不替代需求评审。** 它把矛盾整理成问题清单，但问题得有人答。
- **八类歧义模式是经验清单，不是穷举。** 命中不了不代表没歧义，只是这八类没扫出来。
- **基线变化后模型需复核。** 代码大改（尤其状态机、接口契约）后，第 3、4、5 段必须重新核对，否则模型会悄悄过期。
- **不做跨需求汇总。** 一个需求一份模型，不做需求间的依赖分析。
