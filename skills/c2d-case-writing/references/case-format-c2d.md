# C2D 用例格式细则（case-format-c2d）

> SKILL.md 里只讲骨架，格式硬约束全部在这里。定稿前逐条过，闸门能机判的会自动拦，判不了的靠人。

## 1. 文件结构

```markdown
# C2D 图片校验用例（{项目} / {版本或日期}）

## 导读
（四件套，见第 2 节）

## 场景覆盖表
（规则 / 场景 / 判定 / 理由 / 用例编号）

## 0. 通用说明
（图源策略、环境说明、术语、图例）

## 1. 图片填充模式
### TC-01-01 [P1] ……
### TC-01-02 [P0] ……

## 2. 裁剪与蒙版
……

## 附录 A｜待补图片槽位
## 附录 B｜未核实项（TODO 归属）
## 附录 C｜审查记录
```

## 2. 导读四件套（缺一即闸门报错）

1. **功能与角色**：3 行内说清被测能力（C2D 图片链路走到哪一步）、涉及角色（QA / 研发 / 设计师各看什么）
2. **环境与账号**：被测系统 URL、设计稿文件链接、测试账号。未知项写 `TODO：向 {谁} 索取 {什么}`，不留空
3. **术语表**：只收正文实际出现的词（imageFill / FILL / mask / DPR / object-fit / srcset / CLS…），每条一句
4. **图例**：`[P0] [P1] [P2]`、type 标签、`FIX-*` 槽位含义

## 3. TC 编号

格式 `TC-{模块号}-{序号}`：

- 模块号 = 所在 `## N.` 的一级编号，两位数（`TC-01-03`）
- 序号两位数，模块内连续，不复用已废弃编号
- P0 加 `（SMOKE-n）` 后缀，便于冒烟集抽取：`### TC-01-02（SMOKE-1）[P0] …`
- 编号一旦分配不改；废弃用 `~~删除线~~ + [已废弃-原因]`，不删行

## 4. 五段式字段规范

| 段 | 必填 | 写法要求 |
|---|---|---|
| 规则 | 是 | `IMG-*` 编号 + 触发条件一句话。编号取自 image-rule-matrix，不自造 |
| 前置 | 是 | 设计稿链接/节点 ID、环境、账号、图源槽位。未知写 TODO 带归属 |
| 被测图片 | 是 | **直链 + 特征 + 为何能测到**，三样齐全。预期失败加 `expect_status: NNN` |
| 操作步骤 | 是 | 编号列表，每步一个动作。含"打开什么、点哪里、在哪个视口、看 DevTools 哪一栏" |
| 预期结果 | 是 | 编号列表，每条可判定。含容差与时限 |

**被测图片段的强格式**（闸门按此解析，别改结构）：

```markdown
- 被测图片：https://picsum.photos/id/1015/1200/400
  - 特征：jpeg｜1200×400｜3:1｜103KB｜不透明
  - 为何能测到：{一句话，说明该特征如何让规则被破坏时显形}
```

预期失败的写法：

```markdown
- 被测图片：https://picsum.photos/id/99999/300/300
  - expect_status: 404
  - 特征：故意坏链｜404 text/plain
  - 为何能测到：验证加载失败时是否回退到占位/底色，而非破图图标
```

## 5. 预期结果的判定强度

| 维度 | 可判定写法 | 不可判定写法（禁止） |
|---|---|---|
| 尺寸 | 渲染 375×200（±1px） | "大小正常" |
| 裁剪 | 上下各裁约 20px（±2px），无留白 | "裁剪正确" |
| 填充模式 | `object-fit: cover` | "填充方式对" |
| 格式 | 响应头 `Content-Type: image/webp` | "是 webp 格式" |
| 体积 | ≤500KB | "不太大" |
| 视觉差异 | 差异像素比 ≤2%（阈值来源：{约定/历史分位}） | "看起来一样" |
| 加载 | ≤3s 完成，超时判失败 | "加载较快" |

异步与加载类预期**必须带时限**，无依据的时限要在澄清记录里说明来源，不许拍脑袋。

## 6. 断言范围 ≤ 验证强度

- 只在 1440 视口测过 → 不得断言"全端适配"
- 只测了 Chrome → 不得断言"兼容主流浏览器"
- 只看了一张 3:1 图 → 不得断言"任意比例裁剪正确"
- 只验了响应头 → 不得断言"图片内容正确"

要断更大的范围，就补用例，不改措辞。

## 7. 附录规范（与正文物理隔离）

- **附录 A｜待补图片槽位**：缺什么特征的图、为什么缺、补齐方式、阻塞了哪些规则
- **附录 B｜未核实项**：API 字段名、导出端点、阈值来源等，每条带 `TODO：向 {谁} 确认 {什么}`
- **附录 C｜审查记录**：定稿前自查结果、闸门两轮的退出码、遗留问题

正文里不出现 `文件:行`、函数名、SDK 符号——实现细节进附录 B。

## 8. 审查记录模板

```markdown
## 附录 C｜审查记录

- 审查日期：{YYYY-MM-DD}
- 规则覆盖：include {n} 条 / exclude {m} 条，覆盖率 {n/(n+m)}
- 用例数：{N} 条（P0 {a} / P1 {b} / P2 {c}）
- case_lint_c2d：{修订前退出码} → {修订后退出码}（最终须为 0）
- check_image_links：{通过 n} / {失败 m}（m 须为 0，或失败项均为 expect_status 用例）
- 单图复用告警：{命中条目，人工确认是否合理}
- 遗留 TODO：{条数与归属}
```

计数必须与正文实算一致——闸门会机械核对，估写即报错。

## 9. 紧凑格式

仅在**用户明确要求**或信息密度优先（冒烟清单、快速评审）时使用：可省略"为何能测到"的解释句与图例，但**图片直链、特征、可判定预期三样不可省**。紧凑模式下闸门加 `--allow-compact`，其他检查一项不放松。
