# C2D 图片校验用例编写（c2d-case-writing）

把"图片相关的测试点"写成**每条都挂真实图片链接、且这张图真的能触发该场景**的可执行用例。

## 为什么需要它

图片类 bug 很少出在业务逻辑里，几乎都在**资源与渲染管线的边界**上：填充模式、裁剪、蒙版、透明通道、倍率、格式降级、加载回退。这类 bug 有两个特点：

1. **纯文字描述写不出可执行用例**——"用一张长图测裁剪"，执行者不知道多长、什么比例、什么格式，两个人测出的结论不可比，回归时更没法复现。
2. **图不对等于没测**——用一张 1:1 的图去测 FILL 裁剪，容器也是 1:1，压根不产生裁切，用例"通过"了但什么都没验证到。

所以本 skill 的每条用例都钉死两样东西：**一张具体的图（直链）**，和**这张图为什么能触发这条规则**。

## 落盘产物

| 文件 | 内容 | 维护方 |
|---|---|---|
| `{项目}/测试用例_C2D图片_markmap.md` | 人读用例，**唯一人工维护源** | 人 |
| `{项目}/测试用例_C2D图片.schema.yaml` | 机读元数据，由 markmap 单向抽取 | 脚本 |
| `{项目}/图片素材核验_{日期}.md` | 所有链接的实测结果 | `check_image_links.py` |

Schema 永远可由 markmap 再生，不要求人维护两份；markmap 改动后必须重新抽取。

## When to Use

- 为 C2D 编写图片校验用例（MasterGo 图片填充 / 导出 / 生成代码渲染 / 加载回退）
- 把一份"场景清单"（长图裁剪、webp 降级、透明通道丢失…）落成可执行用例
- 审查既有图片用例：是否每条都挂真图、图的特征是否真能测到点
- 需要按规则编号（`IMG-*`）建立"规则 ↔ 用例"的可回归映射

## When NOT to Use

- 非图片类功能用例（表单、权限、状态机、接口契约）→ `test-case-writing`（qa-skills / 通用用例 skill）
- 需求建模、测试策略与范围决策 → `requirement-analysis` / `test-strategy`
- 把用例转成 Playwright / API 自动化脚本 → `automated-e2e-testing` / `api-testing`
- 只要场景清单、不要用例 → 直接读 `references/image-rule-matrix.md`，不必触发本 skill
- 已确认缺陷的根因定位 → `bug-analysis`

## 五条铁律

1. **一 case 一被测图片**。每条用例正文必须有且只有一个"被测图片"直链（`http://` 或 `https://`）。多图会让预期不唯一，附属图另起用例。
2. **图片特征必须触发场景**。"被测图片"段必须写明格式 / 尺寸 / 比例 / 体积 / 透明性，并一句话说明**为什么这张图能测到这条规则**。特征与场景不匹配（如用 1:1 图测 FILL 裁切）即判用例无效。
3. **禁止占位符与本地路径**。`{图片}`、`<url>`、"示例图"、"某张长图"、`./assets/x.png`、`file://`、`data:image/...` 一律禁止。链接只能取自 `references/image-fixture-registry.md` 或按该文件「自备槽位规范」新增。
4. **链接必须实测可达**。定稿前必须跑 `check_image_links.py`，返回非 2xx 或 `Content-Type` 非 `image/*` 的一律阻断。**预期失败的场景**（404 / 非图片资源）在「被测图片」段显式写 `expect_status: 404`，否则按坏链处理。
5. **预期必须可判定**。禁"显示正常 / 显示正确 / 无问题 / 效果良好"。图片类预期要落到**可测量**的东西：像素尺寸、裁剪边距（±容差）、`object-fit` 取值、Content-Type、体积上限、差异像素比、加载时限。

## 用例格式（五段式 + 一个必填段）

```markdown
### TC-01-01 [P1] 封面图 FILL 模式：3:1 图裁切填满 1.875:1 容器
- 规则：IMG-FILL-03｜触发条件：imageFill 模式 = FILL 且图宽高比 ≠ 容器宽高比
- 前置：设计稿 {文件链接} 页面 {页面名} / 节点 {nodeId}（容器 375×200）；环境 {URL} 账号 {账号}；TODO：向 {谁} 取 {什么}
- 被测图片：https://picsum.photos/id/1015/1200/400
  - 特征：jpeg｜1200×400｜3:1｜103KB｜不透明
  - 为何能测到：3:1 放进 1.875:1 容器必然上下裁切，裁剪量可测（约 20px），裁剪位置可观察
- 操作步骤：
  1. 打开 {设计稿链接}，确认节点 {nodeId} 的填充模式为 FILL
  2. 触发 C2D 生成，拿到产物 HTML
  3. 浏览器 1440×900 视口打开产物，DevTools 选中该图片元素
- 预期结果：
  - 产物中该图为 `<img>`，`src` 为上述直链，`object-fit: cover`
  - 渲染尺寸 375×200（±1px），图片上下各裁约 20px（±2px），无留白、无拉伸
  - 主体宽度与设计稿一致（比例误差 ≤2%）
  - 加载完成 ≤3s；超时仍空白判失败
```

格式细则（编号规则、导读四件套、附录隔离、紧凑格式）见 `references/case-format-c2d.md`，拼装起点见 `assets/case-template.md`。

## 工作流

### 阶段〇｜收输入（开工第一件事，缺一件就停下来要）

主动向用户索取以下四项，缺哪项就在产出里列 TODO 并说明阻塞哪些场景：

1. **设计稿入口**：MasterGo 文件链接 + 页面名 + 关键节点 ID（或一张节点清单）
2. **被测产物形态**：是看生成代码（HTML/组件）、还是看导出的切图、还是看渲染结果
3. **环境与账号**：被测系统 URL、登录方式、是否有可访问的测试数据
4. **图床策略**：公网直链可用吗？内网有图床吗？导出图存在哪、有效期多久（决定用例引用短期签名 URL 还是长期直链）

无设计稿、无产物、无环境时不硬写用例——先说明缺什么、影响哪些场景，让用户决定是补材料还是先出"待执行骨架"。

### 阶段一｜场景盘点（本 skill 的核心步骤）

1. 加载 `references/image-rule-matrix.md`，逐组过 6 组场景（填充 / 裁剪 / 导出 / 代码渲染 / 加载回退 / 视觉一致性）
2. 逐行判断 include / exclude：**exclude 必须写理由**（本期不涉及该能力 / 风险由研发侧兜底 / 无该格式导出），不写理由的一律视为漏测
3. include 的场景标注优先级与档位：必测（P0/P1）/ 边界（P2）
4. 输出「场景覆盖表」附在用例文件导读区之后，格式：

| 规则 | 场景 | 判定 | 理由 | 用例 |
|---|---|---|---|---|
| IMG-FILL-03 | FILL 裁切 | include | 主图位常见，裁剪错了整页看起来就错 | TC-01-01 |
| IMG-FILL-09 | 混合模式 | exclude | 本项目设计稿未使用 blend mode | — |

5. 对 include 的场景，从 `image-fixture-registry.md` 找匹配槽位；**找不到**就在「待补槽位」记一行 TODO，不要用不匹配的图凑

### 阶段二｜澄清（⏸ 检查点，不硬猜）

命中以下任一项必须提问并等待答复，不得自行假设：

| 情形 | 问什么 |
|---|---|
| 设计稿里图片填充模式看不出 | "节点 {id} 的填充模式是 FILL 还是 FIT？我在设计稿只看到裁切后的样子" |
| 产品对超大图没有约定 | "4096×4096 的图（2.6MB）系统是压缩、分片还是拒绝？阈值多少？" |
| 导出图用了短期签名 URL | "这个签名 URL 有效期多久？用例引用它会过期，是否需要长期直链？" |
| 需求写了"支持 webp"但没说降级 | "目标浏览器不支持 webp 时（如旧版微信内核）回退到什么格式？" |
| 预期无量化标准 | "视觉差异的容忍阈值是多少？像素比 2% 还是 5%？来源是什么？" |

预期结果里任何"看着差不多"的地方都是澄清题，不是用例内容。

### 阶段三｜逐场景编写

按场景覆盖表**逐个规则**写，每个规则下按状态/边界展开用例：

- **填充模式**：FILL / FIT / STRETCH / TILE 四档各一条，图片比例必须与容器不同
- **裁剪几何**：圆角、圆形、蒙版、旋转、翻转各一条，图片要带可辨方向或四角内容
- **格式**：png / jpg / webp / svg 各一条，须验证 Content-Type 而不只是"能显示"
- **倍率**：1x/2x（必要时 3x）各一条，断言导出像素 = 设计尺寸 × scale
- **尺寸边界**：1×1 / 常规 / 4096 / 300:1 四档，用边界值法
- **代码渲染**：`src` 可达性、`object-fit` 映射、`alt`、`loading`、`srcset`、路径编码
- **加载回退**：404 / 非图片资源 / 慢加载 / 跨域
- **视觉**：差异像素比 + 色差阈值（阈值必须注明来源）

每写完一个规则组，做一次**自查**（不等到最后）：

1. 本条用例的图，真的能触发这条规则吗？（把图和场景念一遍，问"如果规则破坏了，这张图会让问题显形吗"）
2. 所有预期都能被第三方独立判定吗？（能指出"看哪里、量什么、容差多少"）
3. 有没有两条用例在测同一个点？（有则合并）

### 阶段四｜交付核对（三道，缺一不可定稿）

**核对一：规则覆盖**。场景覆盖表里每个 include 的规则，正文都有对应用例；exclude 的都有理由。漏一个即阻断。

**核对二：图片有效性**。逐条检查：

- [ ] 每条用例都有且仅有一张被测图片直链
- [ ] 每条都写了特征（格式/尺寸/比例/体积/透明性）
- [ ] 每条都写了"为何能测到"
- [ ] 没有占位符、本地路径、`data:` 内联
- [ ] 预期失败的用例有 `expect_status`

**核对三：零上下文可执行**。随机抽 3 条，按"没读过需求、只拿到这份文件"的标准复述：验证什么 → 从哪打开 → 怎么操作 → 怎么算通过 → **用的哪张图、图在哪**。任何一步卡住就改正文或补导读，不降低标准。

### 阶段五｜定稿（两道闸门 + Schema 抽取）

1. **红线闸门**：`python3 <skill目录>/scripts/case_lint_c2d.py {项目}/测试用例_C2D图片_markmap.md`，退出码 1 阻断定稿，按报错行修复后重跑
2. **链接闸门**：`python3 <skill目录>/scripts/check_image_links.py {项目}/测试用例_C2D图片_markmap.md --out {项目}/图片素材核验_{日期}.md`，有非预期失败即阻断
3. **Schema 抽取**：从 markmap 抽取 `测试用例_C2D图片.schema.yaml`，字段含 `id / title / priority / rule / type / image_url / image_traits / expect_status / preconditions / steps / expected / module`
4. 交付时给：用例路径 + 场景覆盖表统计（include/exclude 各几条）+ 核验报告路径 + 未闭环 TODO 清单

## 优先级规则

| 级别 | 判定 |
|---|---|
| `[P0]` | 图片不显示 / 位置错乱 / 格式不支持导致主流程不可用。逐条自检："这条失败，用户还能完成核心操作吗？"答"不能"才是 P0 |
| `[P1]` | 图片显示但有可见偏差：裁剪位置偏、透明度不对、倍率糊、alt 缺失 |
| `[P2]` | 极端尺寸/比例、罕见格式、需特殊环境（弱网、防盗链） |

P0 占比超过 35% 时闸门告警——冒烟集被稀释就失去筛选意义，逐条回炉自检。

## Common Mistakes

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 写"用一张长图测试裁剪" | 不可执行、不可复现、结论不可比 | 钉死直链 + 比例 + 为何能触发 |
| 用与容器同比例的图测 FILL | 不产生裁切，用例"通过"但零验证 | 图比例必须与容器不同，且差异足以观测 |
| 图片链接是本地路径或占位符 | 别人无法执行；回归时链接已失效 | 只取 registry 槽位或自备长期直链 |
| 引用临时签名 URL | 几天后全部 404，用例集整体报废 | 用长期直链；签名 URL 只作"导出结果"断言对象 |
| 只断言"图片显示正常" | 无法判定，执行者各自理解 | 断言像素尺寸、`object-fit`、Content-Type、容差 |
| 一个 case 塞三张图 | 预期不唯一，失败时分不清哪张出问题 | 一 case 一图，其余拆条 |
| 用纯色图测裁剪/蒙版 | 边界看不出来，裁错了也不知道 | 用带四角内容、网格、可辨方向的图 |
| 只测"能显示"不测格式 | webp 被当 png 返回也发现不了 | 断言 Content-Type，不只是肉眼可见 |
| 场景清单写得很全，用例一条不落 | 看着专业，实际没测 | 阶段一就做 include/exclude 判定并留理由 |
| 拿不确定的 API 字段名硬写前置 | 用例前提就是错的，执行必然卡住 | 未核实项写 `TODO：向谁确认什么` |
