## 导读

**功能与角色**：被测能力为 C2D 图片链路——设计稿图片填充 → 平台解析导出 → 生成代码渲染 → 浏览器呈现。QA 关注「图能不能正确显示与回归」，研发关注「导出参数与代码语义」，设计师关注「视觉是否还原」。

**环境与账号**：

| 项 | 值 |
|---|---|
| 被测系统 | {URL} |
| 设计稿文件 | {MasterGo 链接}（页面：{页面名}） |
| 测试账号 | {账号 / 登录方式} |
| 图源 | 公网直链（见附录 A 与 registry）；内网图床 `TODO：向运维确认` |

**术语表**：

- **imageFill**：图片填充，图层 `fills` 中 `type === "IMAGE"` 的 Paint
- **FILL / FIT**：覆盖裁剪 / 完整显示，对应 CSS `object-fit: cover / contain`
- **DPR**：设备像素比，决定位图需要几倍图
- **CLS**：布局偏移，图片未声明宽高比时的典型症状

**图例**：`[P0]` 主流程不可用 / `[P1]` 可见偏差 / `[P2]` 极端边界；`FIX-*` 为 image-fixture-registry 的固定图片槽位。

## 0. 通用说明

- 视口统一 1440×900（除非用例另有声明），浏览器 Chrome 最新版
- 所有图片链接取自 `FIX-*` 槽位，不临时编造；链接核验报告见 `图片素材核验_{日期}.md`
- 判断裁剪量时用 DevTools 的元素盒模型 + 截图取像素，不靠肉眼估

## 1. 图片填充模式

### TC-01-01 [P1] 单图片填充：图与容器 1:1，导出与渲染一一对应

- 规则：IMG-FILL-01｜触发条件：图层 `fills` 仅 1 个 `type === "IMAGE"`
- 前置：设计稿 {链接} 页面 {页面名} 节点 {nodeId}（头像位 300×300）；环境 {URL} 账号 {账号}
- 被测图片：https://picsum.photos/id/1015/300/300
  - 特征：jpeg｜300×300｜1:1｜19KB｜不透明
  - 为何能测到：图与容器同为 1:1，不产生裁切，能把"导出正确性"与"裁剪正确性"解耦——这条只管前者
- 操作步骤：
  1. 打开设计稿，确认该节点填充为单张图片，记录 `imageRef`
  2. 触发 C2D 生成，取得产物 HTML 与导出图
  3. 浏览器 1440×900 打开产物，DevTools 选中该图元素，看 Network 面板
- 预期结果：
  - 导出图为 300×300（scale=1），`Content-Type: image/jpeg`，体积与源图相当（±10%）
  - 产物为 `<img>`，`src` 指向上述直链，加载返回 200
  - 渲染尺寸 300×300（±1px），无留白、无拉伸
  - 同一 `imageRef` 在 Network 中只请求一次（未被重复上传）
  - 加载完成 ≤3s，超时判失败

### TC-01-02（SMOKE-1）[P0] FILL 模式：3:1 图裁切填满 1.875:1 容器

- 规则：IMG-FILL-03｜触发条件：填充模式 = FILL 且图宽高比 ≠ 容器宽高比
- 前置：设计稿 {链接} 节点 {nodeId}（封面 375×200）；图源槽位 `FIX-3X1`
- 被测图片：https://picsum.photos/id/1015/1200/400
  - 特征：jpeg｜1200×400｜3:1｜103KB｜不透明
  - 为何能测到：3:1 塞进 1.875:1 必然产生上下裁切（约 42px 原图高度），裁切量与位置都可测量，规则一旦退化成 FIT 会立刻显形（出现留白）
- 操作步骤：
  1. 打开设计稿，确认节点填充模式为 FILL，容器 375×200
  2. 触发生成，浏览器打开产物
  3. DevTools 选中图片元素，记录 `object-fit`、`object-position` 与盒模型
  4. 截图该区域，量图片上下边缘与容器上下边缘的距离
- 预期结果：
  - 产物 `object-fit: cover`（写死此值，不得沿用默认）
  - 图片铺满 375×200（±1px），上下无留白（留白 >1px 判失败，这是 FILL 退化成 FIT 的典型信号）
  - 上下各裁约 20px（±2px），主体未被裁掉（主体可辨）
  - 无拉伸：图片内圆形物体量出来仍是圆（宽高比误差 ≤2%）
  - 加载完成 ≤3s

### TC-01-03 [P1] FIT 模式：同一张 3:1 图完整显示并留空

- 规则：IMG-FILL-04｜触发条件：填充模式 = FIT
- 前置：同 TC-01-02 的节点，仅把填充模式改为 FIT 后重新生成
- 被测图片：https://picsum.photos/id/1015/1200/400
  - 特征：jpeg｜1200×400｜3:1｜103KB｜不透明
  - 为何能测到：与 TC-01-02 用同一张图形成对照——同一输入、不同模式，结果必须不同；相同即说明模式没生效
- 操作步骤：
  1. 设计稿节点切 FIT，重新触发生成
  2. 浏览器打开，DevTools 选中图片元素
- 预期结果：
  - `object-fit: contain`
  - 图片完整可见，宽度铺满 375，高度约 125，上下各留空约 37px（±2px）
  - 留空区域颜色/透明度与设计稿底色一致
  - 图片比例未失真（宽高比 3:1，误差 ≤2%）

## 2. 导出与格式

### TC-02-01 [P1] webp 导出：Content-Type 必须真的是 webp

- 规则：IMG-EXP-03｜触发条件：导出格式声明为 webp
- 前置：产物配置 `export.format = webp`；图源槽位 `FIX-WEBP`
- 被测图片：https://picsum.photos/seed/c2d/100/100.webp
  - 特征：webp｜100×100｜1:1｜2.9KB｜不透明
  - 为何能测到：源图本身是 webp，若管线把格式转成 png 却仍声明 webp，响应头与扩展名会不一致，这条就是抓这个
- 操作步骤：
  1. 触发导出，取得产物图 URL
  2. `curl -sI {产物图URL}` 看响应头
  3. 浏览器打开产物，确认可正常渲染
- 预期结果：
  - 响应头 `Content-Type: image/webp`
  - URL 扩展名与实际格式一致（`.webp`）
  - Chrome 正常渲染；旧内核不可用属预期，另起降级用例
  - 体积 ≤ 同图 png 版本的 80%（webp 的意义所在）

## 3. 加载失败与回退

### TC-03-01 [P0] 图片 404：必须回退到占位而非破图

- 规则：IMG-FALL-01｜触发条件：图片请求返回 404
- 前置：将节点图片替换为坏链后生成；或用已存在的坏链槽位
- 被测图片：https://picsum.photos/id/99999/300/300
  - expect_status: 404
  - 特征：故意坏链｜404 text/plain｜21B
  - 为何能测到：真实返回 404 且响应体是纯文本（不是图片），能同时验证"状态码处理"与"内容类型不匹配的处理"
- 操作步骤：
  1. 用上述坏链替换节点图片，触发生成
  2. 浏览器打开产物，DevTools Network 确认该请求 404
  3. 观察该图片位区域
- 预期结果：
  - 图片位显示占位底色或 alt 文本，不出现破图图标
  - 布局不塌陷：容器尺寸仍为 300×300（±1px）
  - Console 有可定位的错误日志（含该 URL），不得静默
  - 不阻塞页面其他内容的渲染
